# 선택형 비밀 계정키

사용자 승인: 2026-10-07. 가입 없이 닉네임만 정하는 기본 흐름을 유지한다. 닉네임 화면 하단의 작은 회색 `혹시 기존 계정이 있나요?` 링크를 누른 경우에만 기존 닉네임과 비밀키를 입력한다. 키 생성·변경은 설정에서만 제공하며 사용자가 직접 정한다. 공개 #번호, 이메일 입력, SMTP, 소셜 로그인은 추가하지 않는다.

## 계정과 인증

기존 Supabase UID를 그대로 사용한다. 방·메시지·Storage RLS는 변경하지 않는다. Vercel의 기존 프로젝트에 `/api/account-key`를 추가한다. Supabase 비밀번호 인증에는 내부 이메일 식별자가 필요하므로 서버만 `<uid>@accounts.ping.invalid`를 사용한다. 실제 이메일이나 메일 발송이 아니다. 기존 실사용 이메일 identity는 덮어쓰지 않는다.

사용자 키는 서버 비밀 pepper를 salt로 한 scrypt 지문으로만 private 테이블에 저장한다. 서버가 UID마다 고정된 내부 인증 비밀번호를 HMAC으로 도출한다. 키 변경은 private 지문만 교체하여 기존 기기의 세션을 취소하지 않는다. 서버가 키를 확인한 뒤 표준 Supabase password sign-in으로 기기별 새 세션을 발급한다. refresh token을 복사하지 않는다. 원문 키와 내부 비밀번호는 저장·로그하지 않는다.

닉네임은 기존 검색 정규화를 따른다. 중복 닉네임은 유지하되 동일 닉네임·키 조합은 거부한다. 닉네임 변경 trigger가 로그인 이름을 동기화한다. 키는 공백·대소문자를 그대로 구분하며 12~128자다. 설정에서 연결용 키를 바꿀 수 있고, 키를 잊어도 접속된 기기가 있다면 다시 정할 수 있다. 모든 기기와 키를 잃으면 복구할 수 없다.

## 실패와 운영

잘못된 닉네임·키 입력은 기존 로컬 계정/연결을 바꾸지 않는다. 인증 후 세션 파일을 원자적으로 저장하고 앱 coordinator를 교체한다. 저장 실패 시 받은 세션을 메모리에 보존해 같은 키로 재로그인하지 않고 저장을 다시 시도할 수 있다. 인증 API는 POST만 허용하고 요청 크기 제한, no-store, IP·닉네임별 영속 속도 제한과 일반화된 실패 문구를 적용한다. 신규 RPC는 service_role에만 허용한다.

이번 범위의 로그인은 이 PC에 저장한다. 공용 PC용 메모리 전용 세션과 원격 기기 철회 UI는 별도 작업이다. 로그인 대화상자에서 저장 사실을 명시하며 설정의 `이 PC에서 제거`를 안내한다.

운영 migration, Vercel 환경 변수·배포가 필요하다. 코드 구현만으로 운영 활성화를 주장하지 않는다. 현재 연결된 Supabase 도구는 pinned 프로젝트 접근을 거부하므로 원격 적용은 남을 수 있다. 사용자의 지속 지침에 따라 자동 테스트·빌드·실행·리뷰를 수행하지 않는다.
